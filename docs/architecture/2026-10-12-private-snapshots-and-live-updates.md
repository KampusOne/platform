# Private snapshots and foreground live updates

Status: implemented in the repair branch; native and staging acceptance remains open. Nothing in this record authorizes a production migration, payment or feature activation.

## Storage decision

Use the existing Expo Crypto authenticated AES-GCM API and Expo SecureStore key custody with bounded, versioned AsyncStorage ciphertext. This is a snapshot/draft store, not an offline replica of PostgreSQL. No additional SQLite or paid service dependency is needed for the limited display and draft use cases. Web private data stays in memory. Expo's native cryptography, device restart and key deletion still need physical Android/iOS verification.

The trusted display scope contains the user, institution, sorted student roles and operator roles. Owned drafts, carts, onboarding and personal calendar records use a stable versioned user/institution scope so a role change does not hide unsubmitted work. Profiles, settings, optional telemetry and server display snapshots retain the full role scope. Telemetry expires after 48h, is limited to 300 samples and each foreground flush sends at most 3 samples. Legacy plaintext optional usage is discarded because it has no verified institution scope. A tenant change isolates both kinds of record. Scope and record names are hashed. AAD binds ciphertext to its exact hashed location. Native keys remain in SecureStore; iOS uses WHEN_UNLOCKED_THIS_DEVICE_ONLY. Tokens remain in the separate existing credential store. A scope change immediately clears RAM and increments an epoch so an A → B → A response cannot be reused. Owner-specific writes from an old screen cleanup are rejected before entering RAM or disk.

Allowed snapshots cover academic schedules/GPA/courses/calendar/exams, catalogue/tutorial display and authorised inbox/thread history. Allowed drafts cover academic imports, Kira, publishing, listings, campus activity, message metadata, search recents, onboarding, personal calendar and carts. Unknown records, finance, auth, permissions and quota responses do not acquire durable authority. A cart snapshot never confirms stock, price or payment. Every protected mutation still reaches the Worker.

## Format, bounds and recovery

Payload version 1 contains data, savedAt, expires and an authenticated draft-protection marker. Writes are serialized single-record replacements. The maximum plaintext record is 256 KiB; each scope holds at most 60 records and a conservative 2 MiB ciphertext budget. At most four scopes are retained. Display snapshots and empty completion records can be evicted before owned work; a new write is refused when all available space protects unsubmitted work. Scope eviction also refuses to discard unexpired protected drafts. Oversize records are refused. Native conversation, personal calendar, listing, onboarding, class/calendar/exam imports, campus activities, Kira, publisher and private-answer saves require encrypted read-back before local-save acknowledgement. The draft hooks expose failure, flush work on unmount and prevent completed work from being resurrected; explicit new edits reopen autosave. Browser forms describe session-only retention. Transient editor fields and physical storage-pressure acceptance remain open.

Display reads may reject an invalid record as unusable. Primary draft restoration requires integrity: an absent record or expired empty completion marker may return empty, while bad envelopes, missing keys, decryption failure, malformed authenticated data and expired unsubmitted work produce a visible recovery error. Reads never erase the saved ciphertext on failure. Decoders validate the complete shape before applying any fields; personal calendar arrays cannot silently filter out unreadable dates. Editable fields and replacement autosave remain locked until restoration succeeds, with an explicit retry after a five-second wait deadline. Native storage IO may still finish after this deadline, but abandoned UI results and session changes cannot publish. Warm current work takes precedence over a late decrypt. Per-key write versions are bounded to 256 entries; eviction makes an uncertain old read require retry, while unrelated writes do not interrupt restoration.

Kira retains prompt, mode, manual request ID and recoverable uploaded file metadata. It excludes signed access links, local URIs and extracted bytes from that draft record. A prepared manual retry may retain its original thread context; an ordinary composer opens fresh and saved conversations still reopen explicitly from History. Cached plan data does not grant Pro access. Kira, poll/Q&A and private-answer submission waits for verified local retention. Upload receipts persist before provider reading; extraction failure keeps the uploaded ID. On confirmed response, completion guards prevent an old unmount/autosave from reviving the request. No automatic AI, media or financial outbox is added. A server-confirmed personal date remains confirmed if its device copy fails, with a separate warning and explicit copy-save retry.

Product photo selection uses the existing free crop editor before upload. The six-photo gallery deduplicates URLs and derives its cover from the first item, so preview, reorder, removal and submitted cover agree. Crop cancellation sends no bytes. Picker, editor, byte-loading and staged attachment callbacks are tied to the current session revision; account/campus/role changes dismiss an old crop and reject late results. The physical crop, native file/permission and capture/transfer matrices remain device acceptance gates.

Academic display TTL is seven days; message display snapshots use twelve hours. Owned primary records have no automatic cache expiry and are removed on explicit clearing or logout. Empty conversation completion records expire after seven days. Conversation discovery is limited to 40 active saved threads: a 41st draft is rejected without losing older drafts, and empty threads can be reused. The serialized discovery index is reserved and verified before writing an automatically retryable payload. Corrupt or incomplete snapshot indexes are reconstructed from physical keys; invalid TTLs and authenticated-decryption failures fail closed. Index metadata contains hashed record locations, byte counts, protection flags and timestamps, not user content. Web RAM is bounded to 100 records with owned records retained ahead of disposable views; web drafts remain session-only. The operator must review primary-data retention before release.

Disk and network hydration start together. Late disk results cannot overwrite a fresh server reply or publish after a session revision changes. Retained views display last-synced/stale markers where the screen connects to SyncStatus; the global offline notice preserves usable views. An actual 401/403/404 removes the matching persisted snapshot. A recognised Cloudflare 1010 gateway block preserves the snapshot and credential and reports service access failure. Conversation additionally clears its rendered state after an actual permission denial. Broader screen-specific denial/tenant transitions remain in the acceptance matrix. Cold offline session restoration is not granted from a cached profile: a successful server-established scope is still required.

Legacy plaintext content is not silently trusted. Known draft migrations run only for the matching authenticated owner and remove the old native record only after an encrypted read-back succeeds. Legacy generic private snapshots are scrubbed. Web has no claim of encrypted durable private snapshots. Existing browser attachment blobs have a separate lifecycle and are removed on logout.

## Threat model and limitations

Protected cases: copied AsyncStorage ciphertext, tampering, record swaps, expired records, stale asynchronous writes, tenant/account/role changes, ordinary storage pressure and logout followed by another account. Tests use a Node AES-GCM adapter and simulated storage; they do not substitute for Expo native testing or an independent security audit.

A compromised/unlocked process or rooted device can access decrypted content while the app is authorised. Message media files remain in the OS app sandbox; their bytes are not newly encrypted by this snapshot layer. Retained attachment metadata is encrypted and native draft directories are removed on logout. Do not describe the app as end-to-end encrypted. OS backup/restore, device sharing, SecureStore failure, keychain reinstall behavior and privacy screenshots need device acceptance.

Logout clears the active scope and owner synchronously, destroys discoverable snapshot keys before deleting ciphertext, then removes legacy records and draft files while preserving the files of a concurrent new login. Local credential removal happens before bounded remote revocation on native. Web requires confirmed HttpOnly session removal. Cleanup errors must remain visible; key deletion and storage wiping are not a replacement for session revocation.

Only modern encrypted pending plain text that the user already submitted is automatically retryable. Legacy plaintext recovery strips retry metadata. Account/thread/message/reply identifiers and body bounds are validated, payloads contain only allowed fields, and initial UI send and recovery share one exact intent transfer. One root coordinator retries in the foreground while connected, keeps the original server-idempotent message ID, uses bounded backoff and stops after five failures or a permission/business denial. Logout/session change aborts its work. A newer composer draft is preserved, acknowledgements close only the matching pending intent, and tombstones prevent stale autosaves from resurrecting it. Explicit conflict UI is used before replacing a newer composer with a blocked message. At most 40 pending threads are scanned. Media, payments, payouts, KYC and ledger changes have no automatic outbox. Personal calendar recovery preserves its original request ID for manual retry; it does not automatically submit dates or imports.

## Realtime decision and deployment gate

Use one foreground websocket per signed-in app to a user/institution Durable Object. The stream carries resource invalidations only, never private bodies, prices, identities or location. Existing OS push handles background delivery. PostgreSQL and authenticated HTTP reads remain authoritative.

LIVE_UPDATES_ENABLED and LIVE_USERS are optional and absent from production/staging Wrangler configuration. The new routes return FEATURE_DISABLED without both. No binding, paid feature, migration or production flag was activated. Staging must review capacity and costs and explicitly add a SQLite Durable Object binding/migration before enabling the flag. Do not copy a development binding into production implicitly.

Tickets are issued only for current authenticated sessions, use a dedicated issuer/audience, expire within 60 seconds and are rate limited to 12/minute/user. Tickets travel in the websocket subprotocol, never URL parameters or persistent client storage. Upgrade checks current active user, institution, refresh family, restrictions and browser origin. A hub is isolated by the user/institution tuple, supports at most eight sockets and uses at most a 65-second authorization lease. Restriction/role changes therefore have a bounded lease window; authoritative reads/mutations still check current access immediately.

The hub persists a sequence and the last 128 event IDs. Receivers reject duplicate sequence values and unknown channels. Every reconnect reconciles focused resources; gaps trigger another reconciliation. This is reconciliation, not a durable replay log or cursor-based message delta API. Message mutations publish narrowly to the affected participants. Successful owned notification read changes publish to the current user/institution; community PUSH outbox delivery resolves each notice recipient against current profile and restrictions. Reviewed order/dispatch/delivery/presence mutations publish queue invalidations to the active actor and approved online same-campus riders, capped at 16 recipients to bound subrequests. Publishing is gated before any added query, internal delivery has a 1.5s deadline, and publish failure cannot change a confirmed receipt. In-app-only notice creation, provider-created jobs and full customer/vendor/assigned offline rider audiences remain incomplete; over-cap/uncovered clients retain HTTP fallback.

The client tears down on account/tenant/role change, logout, offline and background/hidden web state. Reconnect uses exponential backoff with jitter capped at 30 seconds and a 10-second handshake watchdog. Feature-disabled responses stop the stream until the next lifecycle availability change. One scheduler supplies focused HTTP fallback; it suspends offline/background and coalesces bursts. Defaults: chat 60 seconds; inbox, notification inbox and rider queue 90 seconds; unread count 60 seconds. Healthy realtime increases contingency spacing up to five minutes. Retry spacing is capped at five minutes. These are calculated configuration bounds, not measured latency improvements; enabling no stream means push or fallback supplies updates.

## Verification and rollback

Isolated Android CI prebuild/Java/Kotlin compilation passes using invalid API origins and a nonfunctional Firebase fixture, with hashes for all eight native modules and asset presence. It produces no APK and does not prove ringing, playback, keychain behavior or device performance.

Portal map, campaign and payment-return readers share one visibility/connectivity listener set and a serial bounded scheduler. Availability does not renew attempt budgets. Map/campaign unchanged states back off to 60s; payment reads stop after 6 attempts until explicit retry. Reload deletes only that portal resource and an older transfer cannot overwrite a newer cached result. One20s portal deadline covers transfer, shared refresh wait, retry and response body.

Root regressions cover ciphertext/account isolation, stale writes, logout key destruction, quotas, deadline handling, 1,000-event burst coalescing, reconnect and listener cleanup. Server integration tests verify ticket issuance, bad signatures/expiry/audience/origin, current institution and revoked sessions. The local workerd smoke verifies upgrade, sequence ordering, duplicate suppression, automatic lease alarm and socket cleanup with a synthetic client whose close-ack timeout is 250 ms. It is not a phone or deployed-network latency test.

Before activation, test actual native websocket behavior, every server event producer, two devices, auth/role restriction, 1,000 events, packet loss, offline restart, foreground/background and cost/connection ceilings. Push and native alarms need separate device proof. Keep realtime disabled if any boundary fails.

Rollback: revert the relevant source phase using normal commits. No production DB migration was made. Encrypted v1 records are ignored by older source; owned records intentionally do not auto-expire, and this version removes them on logout/explicit clearing. The old client must never consume them as plaintext. Unsubmitted drafts should be exported/confirmed before uninstalling or intentionally clearing device data, or before reverting to a version without the same private format. Disable the realtime flag first if a staged deployment is unhealthy; preserve bounded HTTP/push fallback and investigate with correlation IDs. Do not edit financial ledger rows to repair app state.
