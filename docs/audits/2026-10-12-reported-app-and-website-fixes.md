# Reported app and website fixes — 12 October 2026

The user reported stale message badges, failing Android push, a price check on Add to cart, clipped product cards, slow Kira availability checks, missing first-launch onboarding, and separate website/agent sessions. This phase fixes those paths and prepares Android 0.3.26 (version code 56).

## Behavior changes

- Conversation reads carry the last displayed incoming message id. The Worker marks only messages through that boundary and returns the viewer's remaining unread count. Shared badges reject older inbox responses and responses from a previous account or institution. Notification reads use the same visibility rules as the inbox; opening the notification list no longer silently reads every social item.
- Android obtains its native FCM token independently of the Expo relay token. Registration is bound to the current device-cache owner and session. Foreground listeners install before channel setup; resuming after enabling OS permission can recover registration. Verified device checks remain daily, with bounded retries and no global network interval.
- Production push evidence showed 58 `InvalidCredentials` rejections and no admin pause rows. The previous recovery script used an unsupported `account` field and FCM upload mutation. PR #91 corrected those against Expo's official EAS CLI and passed all matching Actions checks before merging. Its production run then confirmed that the project lacked a non-legacy Android credential association. The follow-up creates only the verified package association, reuses matching service-account keys, assigns FCM credentials, and verifies the retained binding. Seven offline credential tests cover these operations. A successful provider setup still requires a phone observation before device delivery is claimed.
- The installed Expo Android SDK parses push navigation/read/observation metadata from a JSON-encoded FCM `data.body`. Direct FCM delivery now uses that envelope as well as the category field; message pushes carry the message id for bounded read actions. This fixes visible notifications whose taps previously had no application route or delivery identifier.
- Add to cart updates local quantities immediately, independently of rate calculation. Stock and one-seller-per-cart rules remain enforced. Cards adapt to one item, narrow phones and larger text; names can wrap, prices can fit, images have retry states, and tapping opens a full product preview with all photos, description, stock and seller details.
- Vendor upload shows `Calculating rates…`, an eight-second deadline, a retry state and a complete price breakdown. Saving checks the previewed policy id against the current campus policy. A price edit invalidates the displayed calculation immediately. Changing an ephemeral policy id does not create a new product request id for an unchanged listing. Checkout retains immutable server quotes and sends the product subtotal plus platform share to the processor, which confirms its charge.
- Kira's fast subscription read enables the plan UI as soon as it succeeds. The additional status read has an independent eight-second budget; the second silent status retry is removed. Store quote/order checks also have eight-second budgets and a synchronous double-tap lock.
- The introduction is completed only by finishing or skipping the walkthrough. Theme or cached profile keys no longer imply completion, and authenticated startup no longer bypasses it. Legacy installs receive one catch-up introduction because the earlier marker did not prove the walkthrough was displayed. Storage restoration and completion have two-second deadlines. Shared links survive the introduction.
- The main website repository is `warriorpikin/kampusone-landing`. Its `/agents`, `/agents/dashboard` and `/agents/payouts` routes use the same root AuthProvider, refresh-cookie transport and sign-in/sign-out as the website. Existing application and dashboard functionality is integrated; links point to the main site. The platform portal redirects legacy `/agents` paths on the agent hostname to the corresponding main-site path after publication.
- The waitlist adds optional faculty, department and a custom level. The additive SQL adds three bounded text columns. The API and website detect schema readiness; existing joins continue working before the migration and no academic values are silently discarded. Anonymous duplicate joins cannot overwrite existing entries. The production addition was then applied within the user’s explicit website-update scope; both existing signups, row-level security and revoked public SELECT privileges were retained.

## Validation

- Worker: 899 tests across 110 files pass, including a real PostgreSQL-engine read-boundary test, private device registration, retry/ledger checks and waitlist storage. A gallery read compatibility failure exposed by the broader suite was corrected with a JSON projection that supports both schemas; all 56 affected business/finance tests then passed.
- Root client regression command: 305 tests pass, including rate calculation/retry, old-response rejection, account changes, native registration without Expo, and account switching during a slow token lookup.
- Mobile and Worker TypeScript pass. Portal TypeScript and lint pass. Mobile web export succeeds; the main website passes TypeScript, lint and a production build with all three agent routes.
- Cache manifest: 501 mounted routes. Source inventory: 85 route entries, six protected main screens, 227 timer/lifecycle sites. These sites include local deadlines and native lifecycle work, not only network polling.
- Local Chromium download was blocked by an incomplete network response. Native compilation and published browser verification must use the release environment; no local phone-render proof is asserted.

## External decisions and release limits

The production database contains no active marketplace commission policy. A configured buyer/platform rate and any seller commission must come from the operator; they are not invented here. The existing quote and payment gates remain intact.

The waitlist migration passed the isolated local PostgreSQL rehearsal. Neon could not create another rehearsal branch because the project’s branch limit was reached; existing branches were not deleted. The additive three-column change was reviewed and applied for the specifically requested website fields. Production checks confirmed three academic columns, both existing signups retained with empty defaults, RLS enabled and no public SELECT permission. No financial tables were changed.

The legal checklist refers to unconfirmed controller/company details, support and address facts, processor/retention rules, refund/renewal/dispute terms and review of the draft policies. Code checks do not confirm those business facts. This phase does not declare all 88 acceptance items complete or the app fully production-ready without the outstanding operator, provider and device evidence.
